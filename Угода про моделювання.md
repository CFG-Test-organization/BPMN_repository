# УГОДА ПРО МОДЕЛЮВАННЯ БІЗНЕС-ПРОЦЕСІВ У НОТАЦІЇ BPMN 2.0

---

## 1. Мета та сфера застосування

### 1.1. Призначення документа

Ця «Угода про моделювання» встановлює єдині обов'язкові правила, стандарти та обмеження щодо графічного опису бізнес-процесів у нотації **BPMN 2.0 (Business Process Model and Notation)**, затвердженій консорціумом Object Management Group (OMG).

Стандарт спрямований на:

* Забезпечення однозначності інтерпретації логіки процесів бізнес-користувачами, аналітиками, аудиторами та IT-розробниками.
* Забезпечення структурної та семантичної цілісності моделей для подальшої регламентації, аналізу вузьких місць або автоматизації у BPMS/Workflow-рушіях (Camunda, Bizagi, Signavio тощо).
* Мінімізацію помилок проектування (виникнення «чорних дір», взаємних блокувань токенів, порушень меж пулів).

### 1.2. Базовий принцип стилю (The Method and Style Principle)

> **Ключове правило:** Логіка виконання бізнес-процесу (усі альтернативні шляхи, винятки, точки очікування та фінальні стани) повинна бути на 100% прозорою, однозначною та зрозумілою **виключно з самої графічної діаграми** — без потреби читати супровідні багатосторінкові регламенти чи вивчати приховані атрибути в XML.

## 2. Концептуальні основи моделювання

| Поняття                                             | Визначення в межах стандарту                                                                                                                                                                                                                                                                                                                         |
| :--------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Бізнес-процес (Process)**              | Послідовність взаємопов'язаних дій, спрямованих на створення цінності для замовника (зовнішнього або внутрішнього), яка має чітко визначену подію старту, завершення та об'єкт управління.                       |
| **Об'єкт управління (Token subject)** | Конкретний бізнес-об'єкт (замовлення, договір, рахунок, скарга, кандидат), стан якого змінюється протягом екземпляра процесу.                                                                                                                                          |
| **Екземпляр процесу (Instance)**     | Одиничне проходження конкретного об'єкта управління маршрутом процесу від стартової до кінцевої події.                                                                                                                                                                               |
| **Токен (Token)**                               | Теоретична концепція переміщення точки управління вздовж потоку. Токен породжується стартовою подією, рухається вздовж потоків управління через активності та шлюзи і поглинається кінцевою подією. |

## 3. Рівні моделювання та зрілості схем

### 3.1. Рівень 1: Описовий (Descriptive / Level 1)

* **Цільова аудиторія:** Власники процесів, топ-менеджмент, бізнес-користувачі.
* **Призначення:** Базове розуміння наскрізного ланцюжка доданої вартості, визначення зон відповідальності підрозділів та ключових контрольних точок.
* **Палітра:** Базові активності (User Task, Service Task), прості розвилки (Exclusive Gateway XOR, Parallel Gateway AND), стартові події без тригера (None) або за повідомленням (Message), кінцеві події (None, Message, Terminate).

### 3.2. Рівень 2: Аналітичний (Analytic / Level 2)

* **Цільова аудиторія:** Бізнес-аналітики, системні аналітики, архітектори рішень, розробники BPMS.
* **Призначення:** Детальний опис логіки з урахуванням граничних випадків, тайм-аутів (SLA), технічних і бізнес-помилок (Error throw/catch), неперериваючих ескалацій та компенсацій.
* **Палітра:** Усі елементи Level 1 + граничні події (Boundary Events), розвилки за подіями (Event-Based Gateways), паралельні та циклічні активності (Multi-Instance, Loop), підпроцеси обробки подій (Event Sub-Processes).

## 4. Архітектурні принципи та декомпозиція (Top-Down)

### 4.1. Правило однієї сторінки (Rule of One Page)

* Кожна діаграма (верхній рівень чи декомпозиція підпроцесу) повинна уміщатися на одному аркуші формату А4 (або одному екрані без горизонтального/вертикального скролу).
* Рекомендована кількість кроків (активностей та шлюзів) на одній схемі — **від 7 до 15 елементів**.
* Діаграми-«простирадла» на десятки кроків **суворо заборонені**.

### 4.2. Ієрархічне моделювання

* Складні, розгалужені етапи оформлюються як **згорнуті підпроцеси (Collapsed Sub-Processes)** з маркером `[+]`.
* Кожен згорнутий підпроцес розкривається на окремому зв'язаному аркуші дочірнього рівня (Child diagram).
* Забороняється розкривати складні підпроцеси inline (розгорнутим прямокутником) на схемі верхнього рівня, якщо це порушує правило однієї сторінки.

### 4.3. Вирівнювання життєвого циклу (Instance Alignment)

* Всі кроки одного пулу повинні діяти над **одним і тим самим екземпляром об'єкта**.
* Якщо в процесі відбувається розщеплення або агрегація (наприклад, 1 замовлення складається з $N$ позицій, кожна з яких комплектується окремо), операції над окремими елементами моделюються як **Multi-Instance (III)** або виносяться в окремий пул із власним екземпляром.

## 5. Правила використання елементів нотації

### 5.1. Пули (Pools) та Доріжки (Lanes)

```
+-------------------------------------------------------------------+
| Пул: Назва процесу                                                |
| +---------------------------------------------------------------+ |
| | Доріжка 1: Роль / Посада                                       | |
| +---------------------------------------------------------------+ |
| | Доріжка 2: Інша роль / Підрозділ                              | |
| +---------------------------------------------------------------+ |
+-------------------------------------------------------------------+
```

1. **Розгорнутий пул (White-Box Pool):**
   * Представляє процес компанії, що моделюється.
   * **Назва пулу — це ЗАВЖДИ назва процесу** (наприклад: *«Обробка замовлення клієнта»*, *«Погодження договору»*). Називати пул назвою компанії («ТОВ Ромашка») або департаменту заборонено.
2. **Згорнутий пул (Black-Box Pool):**
   * Представляє зовнішнього учасника, внутрішня кухня якого нам не підконтрольна (Клієнт, Постачальник, Банк, Державна податкова служба).
   * Не містить всередині жодних подій, шлюзів чи дій.
   * **Помилка:** Заборонено вносити зовнішнього клієнта як доріжку (Lane) всередину пулу внутрішнього процесу компанії!
3. **Доріжки (Lanes):**
   * Позначають внутрішні зони відповідальності: конкретні бізнес-ролі (наприклад, *«Кредитний інспектор»*, *«Головний бухгалтер»*), а не персоналії («Іван Іванович»).
   * Доріжка визначає відповідального **тільки для користувацьких дій (User Task)**.
   * Події та шлюзи розміщуються там, де це мінімізує злами ліній потоку.

### 5.2. Активності (Activities)

```
      [⚙ Service Task]        [  User Task ]        [ Call Activity ]
       (Автоматична)            (Дія людини)        (Глобальний виклик)
```

1. **User Task (Користувацька задача):** Дія, яку виконує людина з використанням програмного інтерфейсу (CRM, ERP, Web-портал).
2. **Service Task (Сервісна задача):** Дія, яка виконується автоматично сервісом, скриптом або інтеграційною шиною без участі людини.
3. **Manual Task (Ручна задача):** Фізична дія поза IT-системами (наприклад, перенесення коробки на складі, підписання паперового акта).
4. **Call Activity (Глобальний виклик):** Посилання на повторно використовуваний загальнокорпоративний процес чи задачу (має потовщену межу).
5. **Multi-Instance Activity (Паралельний або послідовний цикл по масиву):** Позначається трьома лініями `|||` (паралельно) або `≡` (послідовно). Використовується, коли дія повинна повторюватися для кожного елемента списку.

### 5.3. Шлюзи / Розвилки (Gateways)

1. **Exclusive Gateway (XOR — «АБО/АБО»):**
   * Спрямовує токен тільки в одну з вихідних гілок залежно від виконання умови на основі даних.
   * Шлюз **не приймає рішень** — він лише спрямовує маршрут за результатами попередньої задачі (наприклад, задача *«Перевірити скоринг»* ➔ шлюз *«Клієнт платоспроможний?»*).
   * **Обов'язкова умова:** Наявність гілки за замовчуванням (*Default Flow*, позначається косим штрихом `\`) для запобігання зависанню токена.
2. **Parallel Gateway (AND — «I/I»):**
   * *Розгалуження (AND-Split):* розділяє потік на кілька одночасних безумовних гілок.
   * *Злиття (AND-Join):* точка очікування та синхронізації — пропускає потік далі лише після прибуття токенів з **усіх** паралельних вхідних гілок.
   * Гілки паралельного шлюзу підписувати заборонено.
3. **Event-Based Gateway (Розвилка за подіями):**
   * Використовується для очікування альтернативних подій, що змагаються за принципом «хто перший стався» (наприклад: *«Отримано відповідь клієнта»* АБО *«Сплив тайм-аут 3 дні»*).
   * Виходи шлюзу за подіями можуть з'єднуватися **тільки з проміжними подіями-обробниками (Intermediate Catch Events)** або завданнями отримання повідомлень (Receive Task).

### 5.4. Події (Events)

| Тип події                                     | Графічне позначення                                 | Призначення та поведінка                                                                                                                                |
| :---------------------------------------------------- | :-------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **None Start**                                  | Одинарне тонке коло                                  | Ручний запуск співробітником; обов'язковий старт для звичайних підпроцесів.                                  |
| **Message Start**                               | Коло з відкритим білим конвертом          | Старт при отриманні вхідного документа, запиту або повідомлення з іншого пулу.                              |
| **Timer Start**                                 | Коло з циферблатом годинника                 | Запуск за графіком/розкладом (наприклад, щопонеділка о 09:00).                                                                  |
| **None End**                                    | Одинарне жирне коло                                  | Стандартне завершення гілки процесу без надсилання сигналів.                                                             |
| **Message End**                                 | Жирне коло із зафарбованим конвертом  | Завершення процесу з обов'язковим надсиланням відповіді у зовнішній пул.                                        |
| **Terminate End**                               | Жирне коло з жирною кулею всередині     | Миттєве анулювання всіх активних паралельних токенів та завершення екземпляра.                           |
| **Error End**                                   | Жирне коло з блискавкою                           | Завершення гілки критичною бізнес-помилкою; генерує виняток наверх.                                                 |
| **Boundary Event (Перериваюча)**     | Подвійне суцільне коло на контурі дії | Перехоплює помилку або тайм-аут, зупиняє виконання задачі та спрямовує токен на лінію винятку. |
| **Boundary Event (Неперериваюча)** | Подвійне пунктирне коло на контурі      | Запускає паралельний процес (наприклад, нагадування), не зупиняючи виконання самої задачі.        |

### 5.5. Потоки управління та взаємодії

```
Потік управління (Sequence Flow):  ----------------------->
Потік повідомлень (Message Flow):  o - - - - - - - - - - - >
Потік даних (Data Association):    . . . . . . . . . . . . >
```

1. **Потік управління (Sequence Flow):**
   * Суцільна лінія зі стрілкою. Показує черговість кроків у межах процесу.
   * **Синтаксична аксіома:** Потік управління **НІКОЛИ НЕ МОЖЕ** перетинати зовнішню межу пулу або виходити за межі розгорнутого/згорнутого підпроцесу!
2. **Потік повідомлень (Message Flow):**
   * Пунктирна лінія з порожнім колом на початку та стрілкою на кінці.
   * **Синтаксична аксіома:** Потік повідомлень використовується **ТІЛЬКИ між двома різними пулами**! Використання Message Flow між доріжками всередині одного пулу **суворо заборонено**.

## 6. Стандарти найменування (Naming Conventions)

| Елемент BPMN                            | Граматична конструкція                                           | Приклади (Правильно)                                                      | Приклади помилок (Заборонено)                                      |
| :--------------------------------------------- | :------------------------------------------------------------------------------------ | :----------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------ |
| **Задача (Task)**                  | **Дієслово (інфінітив/наказ) + Іменник**           | *«Сформувати рахунок»*, *«Перевірити договір»*   | *«Рахунок»* (це об'єкт), *«Перевірка»* (це функція) |
| **Підпроцес (Subprocess)**      | **Дієслово + Іменник** (комплексна дія)             | *«Провести скоринг позичальника»*                           | *«Відділ ризиків»*, *«Етап 2»*                                     |
| **Шлюз XOR**                         | **Запитання зі знаком «?»**                                  | *«Кредит схвалено?»*, *«Товар є на складі?»*           | *«Схвалення»*, *«Рішення по заявці»*                        |
| **Вихідні гілки XOR**        | **Відповідь або умова**                                        | *«Так»*, *«Ні»*, *«Сума > 100 тис. грн»*                        | Залишати гілки порожніми                                              |
| **Подія старту (Message)**    | **«Отримано [Назва повідомлення]»**                  | *«Отримано заявку на кредит»*                                    | *«Старт»*, *«Початок процесу»*                                   |
| **Подія кінця (End Event)**    | **Іменник + Дієприкметник (досягнутий стан)** | *«Договір підписано»*, *«Замовлення скасовано»* | *«Кінець»*, *«Фініш»*, *«Успіх»*                                |
| **Потік повідомлень**    | **Іменник (назва документа або сутності)**      | *«Заявка клієнта»*, *«Рахунок-фактура»*                 | *«Надіслати листа»* (потік — не активність)             |
| **Об'єкт даних (Data Object)** | **Іменник + [Стан у дужках]**                                 | *«Анкета [Заповнена]»*, *«Договір [Погоджений]»*   | *«Заповнення анкети»*                                                   |

## 7. Графічні та топологічні правила оформлення

1. **Генеральний напрямок:** Моделювання ведеться строго **зліва направо** (*Left-to-Right*) з можливими вертикальними переходами між доріжками виконавців. Рух справа наліво допускається виключно для циклічних петель повернення на доопрацювання.
2. **Ортогональність:** Усі з'єднувальні лінії малюються строго під прямим кутом ($90^\circ$). Діагональні лінії не допускаються.
3. **Мінімізація перетинів:** Перехрестя ліній повинні бути мінімізовані зміною просторового розташування об'єктів.
4. **Узгодження підпроцесів:** Якщо за згорнутим підпроцесом слідує шлюз перевірки результату, формулювання запитання у шлюзі повинно точно відповідати назві однієї з кінцевих подій всередині цього підпроцесу (наприклад, подія *«Кредит схвалено»* всередині підпроцесу ➔ шлюз *«Кредит схвалено?»* на батьківській схемі).
5. **Окремі кінцеві події для різних результатів:** Не змішувати успішні та неуспішні фінали в одну кінцеву подію. Кожен бізнес-результат повинен мати окрему кінцеву подію з чітко зафіксованим досягнутим станом.

## 8. Чек-лист перевірки діаграми перед публікацією

Перед збереженням схеми у корпоративний репозиторій фахівець зобов'язаний верифікувати діаграму за наступними критеріями:

- [ ] **Топологічна замкненість:** Процес містить як мінімум одну стартову подію та як мінімум одну кінцеву подію.
- [ ] **Відсутність "чорних дір" (Black holes):** Немає активностей чи шлюзів, у які входить потік, але звідки немає вихідного потоку.
- [ ] **Відсутність "глухих кутів" (Dead ends):** Немає активностей чи шлюзів без вхідного потоку управління (крім Start Events).
- [ ] **Гігієна Sequence Flow:** Жодна суцільна лінія не перетинає лінію між двома різними пулами чи межу підпроцесу.
- [ ] **Гігієна Message Flow:** Жодна пунктирна лінія повідомлення не знаходиться всередині одного пулу; всі повідомлення починаються і закінчуються на валідних вузлах.
- [ ] **Коректність розвилок:** Усі вихідні гілки шлюзів XOR мають назви умов або відповідей, визначено потік за замовчуванням (Default Flow).
- [ ] **Стандартизація найменувань:** Усі дії сформульовані за правилом «Дієслово + Іменник», події кінця фіксують стан об'єкта управління.
- [ ] **Відповідність правилу однієї сторінки:** Схема легко сприймається без необхідності масштабування нижче 75% на стандартному моніторі.
